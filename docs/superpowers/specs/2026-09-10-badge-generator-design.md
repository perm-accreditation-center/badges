# Спецификация: генератор бейджей для аккредитации

**Статус:** согласовано для планирования, реализация не начата  
**Дата:** 10 сентября 2026  
**Версия первой поставки:** СПО  
**Эталон оформления:** `акушерское дело (1).docx` (используется разработчиками только как визуальный референс; сотрудник его не кладёт во входную папку).

## 1. Назначение и границы первой версии

Программа формирует готовый к печати Word-документ с бейджами членов аккредитационных подкомиссий. Сотрудник получает один исполняемый файл, кладёт присланные документы комиссии в `input`, запускает программу и забирает результат из `output`.

Первая версия поддерживает только присланный формат **СПО**: DOCX-документы с таблицами графика, в которых есть заголовки `ФИО эксперта` и `Статус в составе подкомиссии`. Файл `Аккредитация СПО 2.docx` является контрольным примером такого импорта: в нём обнаружено 15 таблиц с этими заголовками.

Версия не должна:

- требовать установленный Microsoft Word, LibreOffice, интернет или учётную запись;
- принимать шаблон в `input`;
- менять исходные документы;
- молча угадывать структуру будущих документов ВО;
- удалять прошлые результаты из `output`.

Поддержка ВО добавляется позднее отдельным профилем разбора. Общие части — агрегация, вёрстка, создание DOCX, отчёты и терминальный интерфейс — не изменяются.

## 2. Выбранный технический подход

### Рассмотренные варианты

1. **Нативный DOCX/OpenXML на Go — выбранный вариант.** Программа читает XML внутри DOCX и формирует новый DOCX собственной фиксированной разметкой. Это не зависит от Office, работает одинаково на поддерживаемых ОС и позволяет точно задать сетку в единицах Word.
2. Автоматизация Microsoft Word. Подходит только для Windows с установленным Office и создаёт лишнюю зависимость для сотрудников.
3. Запуск LibreOffice в фоне. Кроссплатформен, но требует тяжёлого внешнего приложения и может давать различия верстки между версиями LibreOffice.

Генератор реализуется на Go без внешнего офисного рантайма. Для Windows распространяется `badge-generator.exe`; для macOS/Linux собираются отдельные нативные бинарные файлы. Один `.exe` физически не запускается на всех ОС — это ограничение формата исполняемых файлов, а не Go.

## 3. Пользовательский сценарий и структура папок

Рядом с программой располагаются папки:

```text
badge-generator.exe
input/
  <полученные файлы СПО .docx>
output/
  2026-09-10_153045/
    бейджи.docx
    отчёт.csv
    ошибки.csv                         # только если есть проблемы
```

Сотрудник выполняет только три действия:

1. Закрывает открытые в Word импортные файлы и кладёт один или несколько полученных `.docx` в `input`.
2. Запускает `badge-generator.exe` двойным щелчком.
3. Открывает созданный DOCX из новой папки запуска в `output`, проверяет его и печатает с масштабом 100 %.

`input` не очищается программой. Каждый запуск создаёт отдельную подпапку с отметкой времени, поэтому предыдущие результаты не перезаписываются. Файлы `~$*.docx` (временные файлы Word), не-DOCX и вложенные каталоги игнорируются с пояснением в отчёте.

## 4. Терминальный UX

При запуске открывается обычное окно терминала. Оно показывает понятные этапы, счётчики и итог, но не выводит полный список персональных данных в общем режиме.

Пример успешного запуска:

```text
Генератор бейджей аккредитации — профиль СПО

[1/6] Проверяю папки input и output                 готово
[2/6] Нахожу документы СПО                           2 файла
[3/6] Извлекаю таблицы комиссии                      31 таблица, 87 записей
[4/6] Проверяю и объединяю данные                    64 человека, 23 повтора
[5/6] Создаю Word-документ 9,0 x 5,5 см              64 бейджа, 7 страниц
[6/6] Записываю отчёт                                готово

Готово. Результаты: output/2026-09-10_153045/
Перед печатью выберите «Фактический размер / 100 %», не «Подогнать».
Нажмите Enter, чтобы закрыть окно.
```

Для двойного щелчка окно не закрывается до нажатия Enter. При запуске из уже открытого терминала ожидание отключается параметром `--no-pause`. Параметры не нужны обычному сотруднику.

Ошибка всегда содержит: этап, имя файла, короткое человеческое объяснение, путь к CSV-отчёту и код завершения, отличный от нуля. Например: `Не найден столбец «ФИО эксперта» в файле …; файл пропущен.` Если хотя бы один документ успешно обработан, программа создаёт результат и помечает частичную обработку. Если корректных записей нет, DOCX не создаётся.

## 5. Извлечение данных СПО

### 5.1. Поиск таблиц

Парсер работает не по номеру страницы и не по фиксированной позиции, а по структуре таблицы.

1. Открывает `word/document.xml` каждого DOCX.
2. Находит таблицы, где после нормализации есть заголовки `ФИО эксперта` и `Статус в составе подкомиссии`.
3. Находит специальность в ближайшем предшествующем заголовке вида `… по специальности «…»`. Из неё сохраняется только название специальности без служебной части фразы. Поиск устойчив к разрывам слова между runs Word, например `специальнос ти`.
4. Не предполагает, что значения находятся строго под абсолютными номерами колонок. Сначала находит ячейку с известным статусом `… АПК`, затем берёт ФИО из ближайшей непустой ячейки слева от неё, пропуская служебную метку `Ответственное лицо`. Это обязательно для строк `Ответственное лицо`: в контрольном файле у них значения сдвинуты на один столбец влево. Поиск кандидатов по всей строке допускается только как запасной вариант и всегда отмечается предупреждением: текст в ячейке должности не должен быть ошибочно принят за ФИО.
5. Если заголовок перед таблицей не удалось прочитать, использует специальность в кавычках из статуса как запасной вариант. Непарные или повреждённые кавычки не являются основанием потерять запись.
6. При наличии исправлений Word учитывает актуальный текст и игнорирует удалённый (`w:del`), поэтому отменённая фамилия не попадёт в итог.
7. Строки без ФИО не становятся бейджами. Строки `Ответственное лицо` обрабатываются как обычные записи, если в строке найдены ФИО и роль.

Парсер сохраняет источник каждой записи: имя файла, номер таблицы и номер строки. Это позволяет объяснить любой результат в отчёте.

### 5.2. Нормализация

Перед сравнением программа:

- объединяет разорванные переносами строки и множественные пробелы;
- удаляет только служебную нумерацию в начале значения (`1.`, `2)`), не затрагивая имя;
- приводит кавычки, неразрывные пробелы и регистр к единому виду;
- считает `Ё` и `Е` одинаковыми для сравнения, но печатает первое исходное корректное написание;
- не меняет фамилию, имя, отчество, роль или специальность «по смыслу».

Если ФИО похоже на неполное имя (меньше двух слов), специальность не найдена или строка неоднозначна, запись не выбрасывается автоматически: она попадает в `ошибки.csv` со статусом `ТРЕБУЕТ ПРОВЕРКИ`; сотрудник решает, исправить ли импорт и запустить программу повторно.

### 5.3. Приведение ролей к образцу

На бейдже используются названия из согласованного образца, а не технические названия импорта:

| Значение в импорте (без специальности и организации) | Текст на бейдже |
|---|---|
| `Председатель АПК` | `Председатель подкомиссии` |
| `Заместитель председателя АПК` | `Заместитель председателя подкомиссии` |
| `Секретарь АПК` (в любом регистре) | `Секретарь подкомиссии` |
| `Член АПК` | `Член подкомиссии` |

Организации после роли (`ПГМУ`, `ПБМК` и т. п.) и повтор названия специальности в статусе не выводятся. Неизвестная роль сохраняется без догадок и добавляется в `ошибки.csv` как `НЕИЗВЕСТНАЯ РОЛЬ`.

## 6. Агрегация

Последнее согласованное правило: **один бейдж на одно нормализованное ФИО**, включая человека из строки `Ответственное лицо`.

Для человека программа собирает:

- все уникальные роли;
- все уникальные специальности;
- все ссылки на строки-источники.

Повтор одной и той же пары «ФИО + роль» в документе или между документами не создаёт второй бейдж. Если у одного человека несколько ролей или специальностей, они все печатаются списком на его единственном бейдже. Роли сравниваются уже после приведения к названиям образца. Порядок стабилен: сначала порядок первого появления в импортных документах; повторный запуск с теми же файлами даёт тот же порядок.

Пустая роль печатается как `Роль не указана` и является предупреждением. Пустая специальность печатается как `Специальность не определена` и является предупреждением; скрывать такую информацию нельзя.

## 7. Макет и точный физический размер

### 7.1. Геометрия

Выход — DOCX формата A4, портретная ориентация. На странице ровно 10 бейджей: 2 колонки × 5 строк.

| Параметр | Значение |
|---|---:|
| Внешний размер одного бейджа | **90,00 × 55,00 мм** |
| Размер в Word (twips/DXA) | 5102 × 3118 |
| Ошибка округления единиц Word | менее 0,01 мм |
| Левое и правое поля страницы | 15,00 мм |
| Верхнее и нижнее поля страницы | 11,00 мм |
| Зазор между карточками | 0 мм |
| Сетка на странице | 180 × 275 мм |

Для надёжности DOCX задаёт одновременно фиксированную ширину сетки таблицы, точные ширины ячеек, `fixed`-layout таблицы, нулевой межъячеечный интервал и точную высоту строк. Высота фиксируется правилом `exact`, поэтому карточка не увеличится самопроизвольно; вместо этого перед созданием подбирается размер шрифта и проверяется переполнение.

По контуру каждой карточки выводится тонкая сплошная линия — это линия реза. Карточки соприкасаются краями, поэтому рез делается по общей линии без припуска.

### 7.2. Содержание карточки

Макет повторяет смысл референса и не зависит от входного шаблона:

```text
АККРЕДИТАЦИОННАЯ ПОДКОМИССИЯ
Специальности: <перечень специальностей>

<ФАМИЛИЯ ИМЯ ОТЧЕСТВО>

Роли: <перечень ролей>
```

Текст выравнивается по центру. Семейство шрифта — Times New Roman, как в референсе. Базовый размер — 16 pt; длинный текст автоматически уменьшается ступенями до 8 pt. ФИО — наиболее заметный блок. Для перечней используются переносы строк, а не мелкие абзацы с маркерами.

Если карточка не помещается и при 8 pt, генератор не искажает размер: создаёт бейдж с минимально допустимым текстом и добавляет человека в `ошибки.csv` со статусом `НЕ ПОМЕСТИЛОСЬ`. В терминале показывается счётчик таких случаев. Финальное решение о сокращении формулировок остаётся за сотрудником, а не за программой.

### 7.3. Условие точности при печати

DOCX задаёт размер с точностью формата Word. Фактический рез дополнительно зависит от принтера и его драйвера. В инструкции рядом с программой обязательно будет указано:

1. В Word выбрать бумагу A4 и ориентацию «книжная».
2. Отключить «Подогнать к странице», «Масштабировать» и аналогичные опции драйвера.
3. Печатать «Фактический размер / 100 %».
4. Перед тиражом распечатать одну страницу на целевом принтере и измерить одну карточку линейкой или штангенциркулем: допустимое отклонение — не более ±0,5 мм.

Требование ±0,5 мм относится к готовой распечатке, а не к математически точной разметке DOCX: принтер не может гарантировать более строгую точность без калибровки.

## 8. Результаты и отчётность

Каждый запуск создаёт папку `output/<YYYY-MM-DD_HHMMSS>/`:

- `бейджи.docx` — единственный файл для открытия и печати;
- `отчёт.csv` — все итоговые люди, роли, специальности, число исходных строк, файл/таблица/строка первого появления;
- `ошибки.csv` — только предупреждения и ошибки разбора/переполнения;
- `run.log` — технический журнал без избыточного дублирования персональных данных.

CSV сохраняются в UTF-8 с BOM, чтобы корректно открываться в Excel на Windows. Имена выходных файлов не содержат персональных данных.

## 9. Архитектура для расширения ВО

```text
cmd/badge-generator        запуск, терминал, коды выхода
internal/input             поиск и безопасное чтение файлов
internal/profile           интерфейс профиля импорта
internal/profile/spo       распознавание таблиц и полей СПО
internal/model             Person, Role, Specialty, SourceReference
internal/normalize         очистка и канонизация значений
internal/aggregate         группировка по ФИО
internal/layout            проверка размещения текста и раскладка 2×5
internal/docx              чтение OpenXML и формирование DOCX
internal/report            CSV, журнал, диагностика
testdata                   обезличенные DOCX-фикстуры
```

Профиль ВО реализуется как ещё один модуль `internal/profile/vo`, который выдаёт те же нормализованные записи. Он не получает права изменять правила агрегации или геометрию бейджа без отдельного согласования.

## 10. Проверка и тестирование

### 10.1. Автоматические модульные тесты

| Группа | Кейсы и ожидаемый результат |
|---|---|
| Нормализация ФИО | пробелы, переносы, неразрывные пробелы, регистр, `Е/Ё`, начальная нумерация; идентичные люди объединяются, отображаемое значение сохраняется |
| Нормализация ролей/специальностей | повтор, разные кавычки, переносы; дубликаты исключаются, порядок первого появления сохраняется |
| Агрегация | один человек/одна роль; один человек/две роли; один человек/две специальности; повторы из двух файлов; похожие, но разные ФИО не объединяются |
| Разбор СПО | столбцы в другом порядке, многострочный заголовок, разорванное в runs слово `специальность`, строка «Ответственное лицо» со сдвигом ячеек, пустая строка, пустая роль, отсутствующая специальность, повреждённые кавычки в статусе, ФИО-подобный текст в должности |
| Правки Word | удалённая фамилия (`w:del`) не извлекается, вставленная/актуальная фамилия извлекается |
| Приведение ролей | все четыре согласованные роли, разные регистры `секретарь`, наличие `ПГМУ/ПБМК` после роли, неизвестная роль с предупреждением |
| Безопасность DOCX | повреждённый ZIP, DOCX без `word/document.xml`, слишком большой XML, XML с внешними сущностями; понятная ошибка без аварийного завершения |
| Вёрстка | 1, 2, 9, 10, 11 и 101 бейдж; верное число страниц, заполнение слева направо и сверху вниз |
| Размеры OOXML | каждая колонка 5102 DXA, каждая строка 3118 DXA, A4, поля, fixed-layout, нулевой зазор и exact-height присутствуют в XML |
| Длинный текст | поместился на 16 pt; уменьшился до 8 pt; не поместился и попал в `ошибки.csv` |
| Отчёты | CSV с BOM, безопасные имена, корректные пути и ссылки на источник |

### 10.2. Интеграционные тесты

1. Контрольный `Аккредитация СПО 2.docx`: все 15 распознанных таблиц анализируются; тест проверяет, что ни одна таблица с нужными заголовками не пропущена, что специальные строки `Ответственное лицо` включены и что каждый извлечённый элемент имеет ссылку на источник. Точные правила агрегации дополнительно изолированно проверяются на обезличенных фикстурах с известным ожидаемым результатом.
2. Набор из нескольких DOCX с пересечениями: результат содержит один бейдж на ФИО, а перечни ролей/специальностей не имеют дублей.
3. Смешанная `input`: обычный DOCX, временный `~$`-файл, PDF, вложенная папка и повреждённый DOCX. Валидный документ обрабатывается, остальные документируются без остановки всего запуска.
4. Пустая `input` и `input` без подходящих таблиц: DOCX не создаётся, сообщение объясняет причину, программа завершается с ошибкой.
5. Нет прав на запись в `output`: исходные данные остаются нетронутыми; сообщается путь и действие для сотрудника.
6. Два запуска в одну секунду: директории результата не конфликтуют.
7. Сгенерированный DOCX открывается в Microsoft Word и LibreOffice; проверяется наличие всех страниц, текста, линий реза и отсутствие сообщений о восстановлении файла.

### 10.3. Визуальная и печатная приёмка

Каждая сборка, меняющая DOCX-генератор или макет, проходит:

1. Рендер DOCX в PNG/PDF и просмотр **всех** страниц: нет обрезанного, наложенного, пропавшего текста или лишних пустых страниц.
2. XML-проверку точных размеров таблицы.
3. Открытие в актуальной версии Word на Windows.
4. Тестовую печать страницы с 10 карточками на используемом принтере при 100 %.
5. Измерение минимум трёх карточек: верхней левой, центральной и нижней правой. Ширина должна быть 90,0 мм, высота 55,0 мм в пределах ±0,5 мм.
6. Проверку, что линии реза совпадают между соседними карточками и не съехали относительно бумаги.

Результат считается принятым только после успешных автоматических тестов, визуального просмотра и печатного измерения.

## 11. Критерии готовности первой версии

- Пользователь без настройки запускает программу, положив только файлы СПО в `input`.
- Из корректных таблиц создаётся один бейдж на ФИО с полным списком уникальных ролей и специальностей.
- DOCX содержит ровную сетку A4 2×5, каждая карточка имеет размер 90×55 мм в разметке Word.
- Неподходящие и проблемные записи не исчезают молча: они диагностируются в терминале и CSV.
- Предыдущие результаты и исходные файлы не перезаписываются.
- На контрольной распечатке при 100 % измеренный размер каждой проверенной карточки находится в пределах ±0,5 мм.
- Все автоматические, интеграционные и визуально-печатные проверки из раздела 10 выполнены и зафиксированы перед поставкой.

## 12. Отложенные решения

Не входят в первую версию и требуют отдельной спецификации:

- профиль разбора документов ВО и его контрольный пример;
- ручное редактирование списка перед печатью через графический интерфейс;
- фотографии, QR-коды, штрихкоды и двусторонняя печать;
- печать непосредственно на принтер из программы;
- поддержка XLSX, PDF, сканов или рукописных документов.
